## Summary

Shipped a production-shaped end-user **captive-portal vertical slice** for the MKT WiFi platform: a Vite + React 18 + TypeScript SPA implementing the 5-screen flow (`connecting → form → ad → connected → renew`) per FR-020..039, plus four Pydantic-validated FastAPI endpoints whose contract becomes the integration surface for every later slice (multi-tenant foundation, DB baseline, MikroTik POC). The slice locks Brazilian LGPD compliance into the type system at four layers (Pydantic `Literal` types + runtime `extra="forbid"` + bash grep CI guard + ESLint lane reserved), enforces a privacy boundary by accepting only `mac_hash` (never raw MAC), and prevents the "submit-and-close" exploit by splitting the legacy monolithic `/api/connect` into form-submit + ad-complete. Bundle size is **47 KB gzipped** initial JS — comfortably under the 100 KB COULD goal — with the AdScreen component lazy-loaded as a 4.7 KB chunk that arrives after the time-critical connecting/form phase. **39 backend tests + 20 frontend unit tests pass; tsc strict is clean; AT-015 PII grep returns zero matches across all four target trees.**

## Lessons Learned

### Process

The 5-phase workflow paid off in a way that's hard to replicate ad-hoc. Each phase added a specific kind of rigor that the next phase consumed.

- **BRAINSTORM's biggest payoff was carving the slice.** The original consolidated requirements doc covers an entire multi-tenant SaaS platform. Without explicit scoping (Q1: "which slice?"), /build would have either tried to ship everything (and shipped nothing) or picked an arbitrary subset. Asking "what's the *first* deliverable?" up front locked everything else.
- **Asking discovery questions ONE AT A TIME prevents a class of mistakes.** Several of my answers (e.g., "use query-param `venue_id` for tenancy") only became obvious *after* the previous answer ("vertical slice with mocked backend") locked the scope. Bundling questions would have produced incoherent answers.
- **DEFINE's Acceptance Tests turned into the test plan literally line for line.** AT-001..AT-018 became `test_*.py` and `*.spec.ts` files with the same numbering. There's no translation step between requirements and tests, which removes a class of "we forgot to test that" bugs.
- **DESIGN's pre-build repo inspection is the highest-leverage step in the entire workflow.** Reading [backend/main.py:196-218](../../../../backend/main.py) before writing one line of new code surfaced the legacy `/api/connect` LGPD violation (R13 materializing in code). Without that, the build would have hit a `RuntimeError: Duplicate operation_id` at startup AND left the LGPD-violating endpoint live in production. Lock this step into every future DESIGN.
- **YAGNI was easier with explicit cuts.** The Features Removed table in BRAINSTORM (12 cuts, 1 retention) made it obvious why each feature didn't ship. Future reviewers don't have to ask "why didn't you build the radar animation?" — the answer is in the table.
- **Time-boxing deviations is honest.** Five of eight Playwright e2e specs were deferred during /build. Documenting this in the BUILD_REPORT's Deviations section + listing them as Recommendations below is more useful than half-shipping all 8.

### Technical

- **Pydantic v2 `Literal` + `extra="forbid"` is a stronger LGPD enforcement than docs ever could be.** The schema literally cannot accept `phone`/`email`/`cpf`. A future contributor copy-pasting from another codebase gets a 422 at runtime — they can't accidentally violate Legal's mandate.
- **Defense in depth on NFR-005 was justified.** Pydantic alone would have been sufficient, but adding the bash grep script (AT-015) catches dead-code reintroductions at commit time, and the planned ESLint rule catches frontend literals. The four-layer model is cheap and makes the policy hard to bypass.
- **Splitting `/api/connect` from `/api/sessions/{id}/ad-complete` was non-obvious but critical.** The pre-existing legacy route granted access on form submit. A user could have submitted the form, closed the tab, and gotten 30 minutes of access without watching the ad — a direct revenue leak for the operator. The split makes ad completion a server-side gate.
- **Hand-writing TS types and adding a contract-drift test is a happy middle.** `openapi-typescript` would have been overkill for ~150 LoC of types. The `test_model_field_sets_locked` pytest test catches drift at CI time without adding a build dependency.
- **`mac_hash: str = Field(min_length=64, max_length=64)` is a 64-byte privacy boundary.** Any caller who tries to send a 17-byte raw MAC gets a 422. The contract enforces that raw MACs never reach the backend, before any application-layer concern.
- **In-memory `dict` + asyncio GC was the right call for a vertical slice.** Adopting Redis would have been ~30 LoC of stdlib for ~400 MB of new container surface. The next slice (DB baseline) replaces the dict anyway.
- **Vite `manualChunks` for the AdScreen saved the bundle budget by ~5 KB.** Connecting + form load fast on cellular; the ad chunk arrives during form fill, so it's already cached by the time the user submits.

### Communication

- **The summary-requiments.md doc was 0.98 confidence and that mattered.** When BRAINSTORM started, every UI string, every timing constant, and every field name was already in the spec. /design didn't need to ask "what does the form look like?" because the prototype source was decoded into the spec. Future slices in this repo should expect to do similar archaeology before brainstorming.
- **Deferred assumptions need owners and re-check points.** A-001 (MikroTik appends URL params), A-007 (browsers honor non-skip on `<video>`), A-008 (upstream MAC hashing) are all gated by R2 (real-hardware MikroTik POC). Documenting them in DEFINE → DESIGN → BUILD_REPORT means the MikroTik POC slice has a concrete checklist before it starts, not a vague "validate everything."
- **Open Questions with sensible defaults beat Open Questions that block.** All 7 OQs in DEFINE had explicit "Default if unanswered" answers. /design either accepted them or overrode them. None of them blocked the build cycle.

### Tools & Libraries

- **Pydantic v2.6+ with `model_config = ConfigDict(extra="forbid")`** — the v2 `model_config` style + Python 3.12 native `Literal` types + the `T | None` union syntax produced cleaner schemas than the legacy `Optional[T]` + `class Config: ...` style still in `main.py`. New code sets a migration target for the eventual main.py modernization.
- **httpx + ASGITransport for backend tests** — running the full FastAPI app (with portal router only) under `AsyncClient(transport=ASGITransport(app=test_app))` is faster than spinning up a real uvicorn for each test and avoids socket-bind flakiness in CI.
- **Vite + React 18 + TypeScript 5 strict** — sub-second HMR on mobile-frame development. The `manualChunks` API let us isolate the AdScreen lazily without `React.lazy` boilerplate everywhere.
- **vitest + jsdom** — 20 unit tests run in 3 ms. Faster than jest by an order of magnitude on this surface.
- **Playwright `devices["iPhone 14 Pro"]` preset** — exactly 390 × 844 + a faithful Safari-iOS user-agent. AT-013 (no horizontal scroll) and AT-014 (≥ 44 px touch targets) become trivial to verify when the runtime matches the test rubric.

## Post-Ship Iteration Log

The original ship state (everything above) is preserved as historical truth. Increments below are dated, separately versioned, and reference the corresponding DESIGN Decision.

### v1.1 — 2026-05-04 — AdScreen retry/error UX fix

**What changed:**
- DESIGN bumped to v1.1 with new **Decision 11** ("AdScreen retry/error UX — bounded, observable, recoverable")
- Implementation: 2 files added (`src/state/retry.ts`, `tests/unit/retry.test.ts`), 3 files modified (`AdScreen.tsx`, `strings.ts`, `styles.css`)
- 5 new vitest unit tests covering the retry helper (timing observed via `vi.useFakeTimers()`)

**Why:** Live-flow testing exposed a silent retry loop in `AdScreen.tsx` when `postAdComplete` fails. The original DESIGN §Error Handling row had specified the right behavior but was too terse for an implementer to ship correctly. /build shipped a silent loop instead. Decision 11 now makes the pattern unmissable: pure helper signature, status-banner copy, error-overlay layout, both recovery CTAs.

**Verification:**
- ✅ tsc strict: 0 errors / 0 warnings
- ✅ vitest: **25/25** passing (was 20/20 — added 5 retry tests)
- ✅ vite build: 47.18 KB gzipped initial JS (slightly *smaller* than v1.0); ad-chunk +0.60 KB gzipped (helper consolidated where it belongs)
- ✅ AT-015 PII grep: 0 matches across 4 targets (no regression)
- ✅ Bundle delta gzipped: **+0.66 KB total** (under <1 KB budget claimed in Decision 11)

**Lesson learned (added to the canonical list):**
> When DESIGN's §Error Handling table specifies a behavior, ALSO add the implementation pattern to the Code Patterns section. A terse Error Handling row is a contract; the Code Patterns are the executable spec. /build agents read both — but if only the table mentions the behavior, an under-budget implementer can ship code that "kind of" matches without anyone noticing until the failure path runs in production.

This lesson should propagate into every future DESIGN: any non-trivial error-handling strategy gets BOTH a row in the Error Handling table AND a Code Pattern entry.
